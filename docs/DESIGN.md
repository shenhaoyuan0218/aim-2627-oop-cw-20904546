# 仓库拣货机器人调度系统｜设计与调试记录

## 1. 一张订单如何完成派单

以订单 `O1` 需要 2 件货为例，`Scheduler::submit()` 按下面的顺序处理：

1. 检查订单号、SKU 和数量。数量必须大于 0；订单号和 SKU 必须非空，首尾不能有空白。校验通过后，将订单副本中的 SKU 转为大写。
2. 调用 `Inventory::available_for()`，找出机器人空闲、单站库存至少有 2 件的站点。一张订单只能交给一个站点。
3. 调用当前策略的 `select()`，从候选站中选出一个站点。
4. 调用 `Inventory::reserve()`。预约成功后，站点记下订单号、扣减库存，并将机器人置为 `busy`。
5. 成功后向 `Trace` 追加一条 `DISPATCH` 记录。如果中途拒单，函数返回失败原因，仓库状态和审计记录保持原样。

## 2. 命名空间与职责

| 命名空间 | 主要类型或函数 | 职责 |
|---|---|---|
| `warehouse` | `Order`、`PickStation`、`Inventory` | 保存订单和站点资料。`Inventory` 管理站点注册、查询、候选筛选、预约和完成。 |
| `dispatch` | `DispatchPolicy`、`Scheduler` | 策略负责选站；调度器把订单校验、选站、预约和审计连成一次完整操作。 |
| `audit` | `Trace`、`TraceEvent` | 按发生顺序保存成功事件，可读取或清空记录。 |
| `app` | `valid_station_id()`、`valid_order_id()`、`valid_sku()`、`normalize_sku()` | 提供字符串校验、SKU 规范化和命令行入口。 |

公开声明放在 `include/`，对应实现放在 `src/`。`warehouse/domain.hpp` 只声明领域数据和库存接口，不包含调度策略或 ROS 头文件。仓库实现在检查订单时使用 `app` 的校验函数；`Scheduler` 使用库存、策略和审计接口处理订单。

本地演示和公开测试链接 `aim_oop_core`。ROS 2 包将同一组核心源码编译为 `warehouse_core`，调度节点直接调用 `Scheduler`。Q4 的 `LegacyDispatcher` 是单独编译的旧控制器。

## 3. 两种调度策略如何选择站点

`Inventory` 使用 `std::map` 按站点 ID 保存数据，因此筛选出的候选站已经按 ID 的字典序排列。

假设 S1 有 3 件货、S2 有 10 件货，两站都空闲。同一张订单 O1 需要 1 件，两站都能接单。

| 策略 | 选中站点 | 原因 |
|---|---|---|
| `priority` | S1 | 取候选列表第一项，S1 的 ID 排在前面。 |
| `stock` | S2 | 遍历候选列表，S2 的当前库存最多。 |

`stock` 只在发现库存严格更多的站点时更新选择。如果 S1 和 S2 都有 5 件，遍历到 S2 时会保留 S1，因此库存并列时由 ID 较小的站点接单。

## 4. 状态转换与审计

下表中的 `O` 表示订单号，`S` 表示站点 ID。

| 操作 | 站点库存 | 机器人状态 | 当前订单号 | 审计记录 |
|---|---|---|---|---|
| 派单成功 | 减去订单数量 | `idle` → `busy` | 写入 `O` | 追加 `DISPATCH O S` |
| 完成成功 | 保持当前值 | `busy` → `idle` | 清空 | 追加 `COMPLETE O S` |
| 派单失败 | 保持 | 保持 | 保持 | 无新增 |
| 完成时站点或订单号错误 | 保持 | 保持 | 保持 | 无新增 |
| 重复完成同一任务 | 保持 | 保持 `idle` | 保持为空 | 无新增 |

例如，S1 持有 O1 时，调用 `complete("S1", "O2", reason)` 会失败，S1 继续执行 O1。只有站点存在、机器人正忙、当前订单号完全匹配时，才能释放机器人。完成后库存保持扣减后的数值，因为货已经拣走。

## 5. Q4 缺陷复现与修复

`src/debug/main.cpp` 自带固定事件，不需要从键盘输入。初始库存为 S1=3、S2=5，两台机器人均空闲：

1. 提交 O1，数量为 2。S1 接单，库存从 3 变为 1。
2. 提交 O2，数量为 6。跳过忙碌的 S1，检查 S2。S2 只有 5 件，应拒绝订单并保留库存 5。
3. 完成 O1，S1 恢复空闲，库存仍为 1。
4. 提交 O3，数量为 1。S1 库存恰好足够，接单后变为 0。

| 运行版本 | 实际输出 |
|---|---|
| 初始提交 `72c9150` 中的原程序 | `S1 no -1 yes 0` |
| 修复后的程序 | `S1 no 5 yes 0` |

**根因。** 旧代码先执行 `item.second -= quantity`，再判断 `item.second < 0`。处理 O2 时已经把 S2 的库存从 5 改成了 −1。随后的 `return` 结束了函数，此前的扣减仍然生效。

**修复。** 先拒绝数量小于等于 0 的订单，再按站点 ID 顺序跳过忙碌站。遇到第一个空闲站时，先比较库存和需求；库存不足就立即拒绝，库存足够才扣减、置忙并写入订单号。

这一点与 Q1 有区别：若 S1=1、S2=5，两站空闲，订单要 2 件，Q1 会筛选出 S2；Q4 按旧控制器的约定，在首个空闲站 S1 作出拒绝决定。
